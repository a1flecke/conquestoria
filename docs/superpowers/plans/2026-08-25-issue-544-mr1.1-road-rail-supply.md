## Design (re-derived from contract + repo-mapping spec, verified against
## current code before writing this plan)

**Contract §9, verbatim requirements:**
- Roads/rails are "bounded logistics amplifiers, not supply lines."
- They do not create supply, do not trace unlimited networks, can extend a
  nearby valid source by a bounded amount.
- Hybrid progression: source type gives baseline reach (already MR1); a
  logistics tech improves categories; infrastructure (`hasRoad`) contributes
  the bounded extension.
- "Road/rail extension scales with technology, not source type" — i.e. one
  flat bonus amount applied uniformly whether the nearby source is a Fort,
  Citadel, or City, not a per-source-type multiplier.

**Repo-mapping spec's Finding 1 (§4) resolves the exact tech gate:** this
codebase has one `hasRoad` tile flag, no separate rail tile
(`src/core/types.ts:396`). `road-network.ts`'s `resolveTileHasRail` already
derives "does this road tile render as a railroad" from `hasRoad && owner
!= null && ownerCompletedTechs.includes('railway-expansion')` — purely
presentational today. The movement-cost mechanic
(`.claude/rules/game-balance.md`'s "Roads discount, they don't stack") gates
the SAME two techs, `military-logistics` and `railway-expansion`, never
stacking. MR1.1 must reuse these same two techs (not `road-building`, which
only unlocks the *ability* to build roads) for the supply-radius bonus, and
must not stack them — matching the movement-discount precedent exactly and
the Fort/Citadel `getFortificationTier` one-flag/one-tier convention.

**Verified against current code (`src/systems/supply-sources.ts`, read in
full before writing this plan):**
- `getLandSupplySourceCoverage(state, civId, coord, candidates)` and
  `getPrimarySupplySource(state, civId, coord, candidates)` are the two
  canonical resolution functions — confirmed via grep, every real caller
  (`supply-system.ts`'s `resolveLandSupplyForCiv`, MR2's
  `supply-overlay-presentation.ts`, `selected-unit-info.ts`'s unit-panel
  status line) goes through these two, nothing else. Extending these two
  functions extends every consumer for free — the "one canonical resolution
  hook" this codebase already established.
- Both currently do a flat `mapDistance(source, coord) <= radius` check, no
  road awareness at all.
- `mapNeighbors(state.map, coord)` (`hex-utils.ts:155`) is the existing
  wrap-aware adjacency helper (already used by `fortification-system.ts`) —
  reuse it rather than hand-rolling wrap-aware neighbor math again.

**The extension itself:** a coord gets a bonus to whichever source radius is
being checked against it if the coord itself, or any of its wrap-aware
neighbors, is an owned tile with `hasRoad: true`. Deliberately **not** a
network trace — `getCitiesConnectedToCapital` (`road-network.ts`) already
demonstrates what a real road-network BFS looks like in this codebase, and
MR1.1 must NOT reuse that pattern (that's exactly what contract §9's "do not
trace unlimited networks" prohibits for supply specifically, even though the
same BFS is legitimate for the unrelated capital-connectivity mechanic it
already serves). The bonus is purely local: check `coord` and its immediate
neighbors, nothing further.

**Values** (contract §29: "road/rail extension values" explicitly left open,
not locked — chosen here, easy to retune via one exported constant object):
`military-logistics` → +1, `railway-expansion` → +2 (tiered, not additive —
having `railway-expansion` means "use the rail tier," not "add both").
Small relative to the existing `LAND_SUPPLY_RADII` (fort 1, citadel 2, city
3), matching "bounded... small" from the contract and design spec both.

## Scenario matrix mapping (contract §30 items 11-14)

- **11. Bounded road extension** — a unit on/adjacent to an owned `hasRoad`
  tile, owner has `military-logistics` (not `railway-expansion`), gets the
  road-tier (+1) bonus.
- **12. Bounded rail extension** — same, but owner has `railway-expansion`
  (regardless of also having `military-logistics`, matching the movement-
  discount precedent's non-stacking rule) — gets the rail-tier (+2) bonus,
  not both added together.
- **13. Correct tech category improvements** — negative coverage: (a) a unit
  on/adjacent to a road tile whose owner has *neither* tech gets zero bonus;
  (b) a unit NOT on/adjacent to any road tile gets zero bonus even with both
  techs completed (the tech alone creates nothing — infrastructure must
  exist, matching "they do not create supply" from §9).
- **14. No unlimited traced network** — negative coverage: a long chain of
  connected owned road tiles does not let a unit far from both the chain's
  starting few tiles AND any real source receive coverage — only immediate
  on/adjacent-to-road-tile positions get the bonus, proving there is no BFS
  propagation happening.

```ts
/**
 * Bounded, tech-gated coverage bonus for a coord on/adjacent to an owned
 * road tile (contract §9: "extend a nearby valid source by a bounded
 * amount... road/rail extension scales with technology, not source type").
 * Mirrors getFortificationTier's "one flag, owner-tech-derived tier"
 * convention: hasRoad is the single persisted flag (no separate rail tile,
 * see road-network.ts's resolveTileHasRail for the identical precedent);
 * which tier applies is derived purely from the checking civ's completed
 * techs. Gates on military-logistics/railway-expansion -- the same two
 * techs the movement-cost discount already uses, never both stacking
 * (.claude/rules/game-balance.md's "Roads discount, they don't stack").
 * Deliberately NOT a network trace: checks only coord and its immediate
 * wrap-aware neighbors via mapNeighbors, so a long chain of connected road
 * tiles cannot extend supply an unbounded distance (contract §9: "do not
 * trace unlimited networks" -- see getCitiesConnectedToCapital in
 * road-network.ts for what an actual road-network BFS looks like in this
 * codebase; this function must never grow into that).
 */
export function getRoadSupplyExtension(state: GameState, civId: string, coord: HexCoord): number {
  const completedTechs = state.civilizations[civId]?.techState.completed ?? [];
  if (!completedTechs.includes('military-logistics')) return 0;

  const isOwnedRoadTile = (candidate: HexCoord): boolean => {
    const tile = state.map.tiles[hexKey(candidate)];
    return tile?.hasRoad === true && tile.owner === civId;
  };
  const nearRoad = isOwnedRoadTile(coord) || mapNeighbors(state.map, coord).some(isOwnedRoadTile);
  if (!nearRoad) return 0;

  return completedTechs.includes('railway-expansion') ? ROAD_SUPPLY_EXTENSION.rail : ROAD_SUPPLY_EXTENSION.road;
}
```

Add `mapNeighbors` to the existing `hex-utils` import at the top of the file
(currently `import { hexKey, mapDistance } from './hex-utils';`).

Now hook it into both resolution functions — each computes the extension
**once** (it depends only on `coord`/`civId`, not on which source is being
checked, so it must not be recomputed inside the per-source loop):

```ts
export function getPrimarySupplySource(
  state: GameState,
  civId: string,
  coord: HexCoord,
  candidates: CivSupplySourceCandidates = getCivSupplySourceCandidates(state, civId),
): SupplySourceRef | null {
  const ranked: Array<SupplySourceRef & { distance: number }> = [];
  const roadExtension = getRoadSupplyExtension(state, civId, coord);

  for (const city of candidates.cities) {
    const distance = mapDistance(state.map, city.position, coord);
    if (distance <= LAND_SUPPLY_RADII.city + roadExtension) ranked.push({ kind: 'city', id: city.id, coord: city.position, distance });
  }
  for (const fortCoord of candidates.fortCoords) {
    const distance = mapDistance(state.map, fortCoord, coord);
    if (distance <= candidates.fortRadius + roadExtension) ranked.push({ kind: 'fort', id: hexKey(fortCoord), coord: fortCoord, distance });
  }

  if (ranked.length === 0) return null;
  ranked.sort((a, b) => a.distance - b.distance || hexKey(a.coord).localeCompare(hexKey(b.coord)));
  const { distance: _distance, ...ref } = ranked[0]!;
  return ref;
}

export function getLandSupplySourceCoverage(
  state: GameState,
  civId: string,
  coord: HexCoord,
  candidates: CivSupplySourceCandidates = getCivSupplySourceCandidates(state, civId),
): boolean {
  const roadExtension = getRoadSupplyExtension(state, civId, coord);
  for (const city of candidates.cities) {
    if (mapDistance(state.map, city.position, coord) <= LAND_SUPPLY_RADII.city + roadExtension) return true;
  }
  for (const fortCoord of candidates.fortCoords) {
    if (mapDistance(state.map, fortCoord, coord) <= candidates.fortRadius + roadExtension) return true;
  }
  return false;
}
```
